FriendsLy - Social Spontaneity & Intent-Based Social Networking App

1. Introduction
1.1 Purpose
The purpose of this document is to provide the functional and non-functional requirements of FriendsLy ,a privacy first intent driven social network application. It serves as a reference point for developers, UI/UX designers, stakeholders or interested parties and project managers during design, development, testing and deployment.
1.2 Scope
FriendsLy is a social networking app that promotes real-world social interaction through mood-based presence, spontaneous meetings and lightweight communication tools.
FriendsLy, unlike popular social media platforms such as Instagram, TikTok, and WhatsApp, focuses on.
Physical Presence.
Intent-based hangouts.
Privacy preserving.
Spontaneous and low pressure engagement.
ALow-key, minimal ,calm and social design.
The system will facilitate content sharing and discovery, communication, privacy controls, with a priority on user safety and data transparency.
1.3 Definitions
SRS - Software Requirements Specification
Aura - A temporary mood + intent broadcast
Serendipity Engine - Algorithm suggesting spontaneous connections
Capsule - Ephemeral memory created during meetups
Intent - User-declared activity desire (e.g., coffee, walk, study)

2. Overall Description
2.1 Product Perspective
FriendsLy is a cross-platform mobile application (Android & iOS) supported by a cloud-based backend infrastructure and centralized database.
The system consists of:
Mobile client (User Interface)
Backend API services
Real-time communication server
Encrypted messaging module
AI-powered personalization engine

3. Functional Requirements

3.1 User Account Management
 FR1: The system shall allow users to register using email or phone number.(DONE)
 FR2: The system shall require profile creation (name, photo, interests).(DONE)
 FR3: The system shall allow profile editing.(DONE)
 FR4: The system shall allow account deactivation.
 FR5: The system shall allow permanent account deletion.
 FR6: The system shall allow users to download their data.
 FR7: The system shall verify email address or phone number during registration.(DONE)
 FR8: The system shall automatically terminate inactive sessions after a defined timeout period.
 FR9: The system shall allow users to log out from all active devices simultaneously.

3.2 Social Aura System (Core Feature)
FR10: The system shall allow users to create a Social Aura.
 FR11: The Aura shall include intent selection (e.g., coffee, walk).
 FR12: The Aura shall allow visual customization (color, emoji, glow).
 FR13: The system shall display approximate proximity only.
 FR14: The system shall notify users of auras overlapping.
 FR15: Users shall be able to accept, decline, or snooze aura suggestions.

3.4 Serendipity Engine
FR16: The system shall analyze intent and proximity patterns.
 FR17: The system shall suggest spontaneous hangouts.
 FR18: The system shall allow users to opt out of suggestions.
 FR19: The system shall log suggestion reasoning for transparency.

3.5 Content Creation & Sharing
 FR20: The system shall support 24-hour ephemeral stories.
 FR21: The system shall allow photo posts.
 FR22: The system shall allow video posts.
 FR23: The system shall allow short text micro-blog posts.
 FR24: The system shall provide privacy controls (friends-only, close friends, public).
 FR25: The system shall support collaborative posts.

3.6 Interaction & Communication
FR26: The system shall support voice notes in chat.
 FR27: The system shall support polls for hangouts.
 FR28: The system shall implement end-to-end encrypted messaging.

3.7 Group Chats
FR29: The system shall create a temporary group chat upon Hangout confirmation.
 FR30: The group chat shall allow text messages, polls, and shared notes.
 FR31: The group chat shall automatically delete after event completion by default.
 FR32: The system shall allow users to convert the temporary group chat into a permanent group chat before deletion.

3.8 Hangout Capsules
 FR33: The system shall allow confirmed attendees to co-create a Hangout Capsule after or during a meetup.
 FR34: The Hangout Capsule shall function as a digital time capsule summarizing the hangout.
 FR35: The capsule shall automatically include structured information such as hangout type, date, time, location, and list of attendees.
 FR36: The capsule shall allow attendees to add photos, short videos, audio clips, and short written reflections.
 FR37: The system shall auto save photos and videos from the temporary group chat into the Hangout capsule.

3.9 Intent-Based Hangouts
FR38: The system shall provide predefined hangout intents (Coffee, Walk, Study, etc.).
FR39: The system shall allow one-tap hangout creation.

3.10 Discovery & Explore
 FR40: The system shall provide a friend feed.
 FR41: The system shall display nearby highlights.
 FR42: The system shall provide curated Explore content.
 FR43: The system shall display trending local activities.

3.12 Privacy & Safety
 FR44: The system shall provide granular visibility controls.
 FR45: The system shall allow emergency trusted contacts.
 FR46: The system shall provide notification management controls.
 FR47: The system shall provide block and report functionality.

3.13 Accessibility & UX
FR48: The system shall support dark mode.
FR49: The system shall provide customizable themes.




4. Non-Functional Requirements
4.1 Performance
NFR1: System response time shall be less than 2 seconds for standard actions.
NFR2: Real-time aura matching shall occur within 5 seconds.
4.2 Security
NFR3: All sensitive data shall be encrypted at rest and in transit.
NFR4: Multi-factor authentication shall be supported.
4.3 Reliability
NFR5: Data backup shall occur daily.
4.4 Usability
NFR6: The interface shall follow calm, minimal design principles.
NFR7: Average onboarding completion time shall be under 3 minutes.
4.5 Scalability
NFR8: The system shall support horizontal scaling for increasing users.
